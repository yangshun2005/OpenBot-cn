# Composio

Composio 是一个代理服务。它代管人们在数百个应用中的账户——Slack、Linear、Gmail、HubSpot 以及它们背后的一长串应用——并将每个应用的操作发布为工具，本部署可以代表某人调用这些工具。无需注册 OAuth 客户端，无需粘贴密钥，也无需逐字符匹配重定向 URI，因为账户并不在这里：用户向 Composio 授权，Composio 持有返回的结果。被授予代理操作的 Bot 会**以提问者本人的身份**访问该应用，与本部署中其他所有按人连接的连接器一样，因此两个人问同一个问题，得到的是各自账户所能看到的答案。

设置它需要三方参与，任何一方都无法代劳另一方：

| 角色             | 做什么                                                                     | 在哪里                                                             |
| ---------------- | -------------------------------------------------------------------------- | ----------------------------------------------------------------- |
| 部署者           | 设置 `COMPOSIO_API_KEY`                                                    | 部署的环境变量，或 Helm chart 中的 `secrets.composioApiKey`。没有对应的界面 |
| 管理员           | 启用应用                                                                   | `/admin/plugins/composio`                                         |
| 管理员           | 将其操作授予某个 Bot                                                       | `/admin/plugins/composio-<slug>`，然后是该页面的按 Bot 界面       |
| 每个人           | 将自己的账户连接到该应用                                                   | `/settings/connected-accounts`                                    |
| 管理员           | 为应用选择 Personal 或 Shared，并连接 Shared 应用的账户                    | `/admin/plugins/composio-<slug>`                                  |

密钥这一行是最容易误读的，所以这里说两遍：它是一个环境变量，仅此而已。任何管理员，无论权限多高，都无法从页面上开启 Composio，`/admin/plugins/composio` 是已设置的密钥被使用的地方，而不是设置密钥的地方。

管理员**无法以他人的身份**连接账户，这是刻意为之。Shared 应用是另一回事：它的账户属于部署，而不属于任何个人，审计追踪在每次调用时都会说明这一点，管理员从应用自己的页面以团队身份连接它。

## 密钥

`COMPOSIO_API_KEY` 是整个部署共用的一个密钥，且是可选的。它是唯一的 Composio 设置——没有按应用的设置，也没有按人的设置。一个密钥并不意味着一个共享账户：Composio 通过每次调用时发送的用户 id 将人们区分开来，因此一个人的连接永远无法被另一个人访问。

启动时不会验证密钥。没有可用来检查它的格式，也没有值得在启动时发起的调用来验证它，所以第一个真实请求才能说明它是否有效。下面的 `composio:smoke` 是运维人员主动提出这个问题的方式，而不是通过观察别人失败来发现。

未设置是一种受支持且完整描述的状态，而非降级状态：这是当前每个部署的状态。没有密钥时屏幕上显示的内容恰好是一行，位于 `/admin/plugins` 的 **More apps** 标题下，标题为 *Composio*，内容为 *Add your Composio key to enable a catalogue of tools. Set COMPOSIO_API_KEY on this deployment.* 它没有折叠箭头，也不是链接，因为在设置密钥之前无处可去。它指明了设置项而非隐藏该功能，因此听说过 Composio 的管理员可以了解它需要什么——而且由于它上方的标题也保留着，那少数几个经过审核的连接器不会读起来像是全部内容。

这一行就是全部。没有可浏览的目录，没有选择器，任何人的已连接账户页面上都没有代理应用，Bot 也没有可调用的 Composio 工具。

在设置了密钥时启用的应用，之后密钥被移除，会保留其行和授权。它的页面会说明密钥缺失，其调用会以一句同样内容的话拒绝——与这里其他地方一样，与“该应用未发布任何内容”区分开来。

### 查询此密钥能看到什么

```
COMPOSIO_API_KEY=... bun run composio:smoke -- --user <id> [--call]
```

`scripts/composio-smoke.ts` 是当 Composio 出现异常而屏幕上没有任何说明时应该运行的唯一命令。它随容器镜像一起发布，因此在密钥所在的地方运行——在部署中，而不是在笔记本电脑上——它回答了没有任何页面能回答的问题：*这个*密钥是否能打开*这个*项目。一个背后没有项目的密钥、一个没有该应用授权配置的项目，以及一个从未完成授权页面的用户，都会留下一个看起来已配置但什么都不响应的产品。

**它将密钥与用户区分开来，这是三者中的两者，而非全部。** 目录读取回答的是密钥的问题：Composio 拒绝的密钥，以及目录中不包含该应用的项目，都会以厂商自己的语句终止运行。连接读取回答的是用户的问题。它没有区分的是授权配置——管理员在此处未启用的应用没有任何配置可供任何人连接，因此它读起来与从未完成授权的用户完全一样，无连接的那行会说明这一点，而不是归咎于用户。查看 `/admin/plugins` 下该应用的页面来区分这两者；启用应用才会创建配置。要让脚本本身区分它们，需要在代理接缝上提供一个只读的授权配置列表，而目前尚不存在——该接缝有 `ensureAuthConfig` 和 `deleteAuthConfig`，两者都会写入，而只读诊断绝不能创建它被要求查找的对象。

**它列出每个应用解析后的连接类型，并对类型进行统计，因为静默失败恰恰存在于那里。** 每个应用一行，包含 slug、本部署解析出的类型及其操作数量——对于 `fields` 类型的应用还包括方案，`fields: API_KEY`，因为一个应用解析为 API_KEY、BASIC、BEARER_TOKEN 还是 BASIC_WITH_JWT，决定了连接表单要求用户输入什么。类型是从目录行读取的，而不是在这里再次推导，因此诊断结果永远不会与产品在应用如何连接上产生分歧。这些行下方是一个统计：`Kinds: consent 121, self-registering 86, fields 1243, no auth 34, unsupported 56.` 每个已知类型都以零为种子，以便零值也能打印出来，这正是其意义所在——解析会将格式错误的 `auth_schemes` 读作空列表，因此厂商重命名或重塑该字段会导致*每个*应用都解析为 `unsupported`，而选择器会隐藏不支持的应用。从其他任何角度看，这个失败都不会说什么：目录列出其通常的四个数字，目录响应 200，但没有一个应用被提供。`Kinds: consent 0, self-registering 0, fields 0, no auth 0, unsupported 1540` 就是那种状态，无需任何人滚动就能读出来。之后要针对报告所涉及的应用进行 grep 的，就是那些按应用的行。

它全是读取操作。它不生成连接链接，也不启动会话，因为链接是一种持有者凭证，打印出链接的诊断会把某人的邮箱留在终端的回滚缓冲区中。密钥也从不打印：每一行都经过脱敏器输出，包括厂商自己的语句，那是唯一包含非本处所写文本的行。`--user` 接受本部署作为调用对象发送给 Composio 的 id——与 `composio_connections` 记录的 id 相同。`--call` 额外运行一个只读操作 `GMAIL_GET_PROFILE`，并且只在调用时检查 Composio 自己的行为标签之后才运行，而不是信任其名称。

**一行输出到哪个流由它所解释的退出码决定。** 解释非零退出的行写入 stderr；其他所有行写入 stdout。因此 `… > report.txt` 保留了密钥能看到什么的报告，而命令失败的所有原因仍然在旁边的终端上——一个运行了但失败的操作会将其结果和日志 id 放到 stderr，因为这两行就是它退出码 `1` 的完整解释。退出码为 `0` 表示运行完成，`1` 表示运行停止，`2` 表示缺少 `--user`。

## 管理员做什么

### 1. 找到应用，并阅读其操作数量

在 `/admin/plugins/composio`，搜索 Composio 的目录。目录会被读到末尾——逐页读取，跟随 Composio 自己的游标——并在本进程中搜索而非在厂商处搜索，因此屏幕上显示的是完整列表，而不是其中一页。

**它是完整的可连接列表，而非完整目录。** 需要由本部署的运维人员注册 OAuth 应用的应用在搜索运行之前就被过滤掉了：Composio 在 2026-09-13 发布的 1540 个应用中有 56 个，被隐藏是因为这里无处放置客户端 id 和密钥，而一个只会遭遇拒绝的 **Add** 按钮比一个诚实地缺席的应用更糟。其他所有类型都会被提供。每种类型要求什么、向谁要求，是下一节的内容。

每一行都带有应用的**操作数量**，在按下 **Add** 之前值得读一读这个数字。Slack 发布了 167 个操作，其中 73 个是读取——比模型能良好处理的量多出好几倍。没有上限：授权仍然是唯一的天花板，因此大型应用是可能的，只是永远不会是意外发生的。

### 2. 启用应用

**Add** 接受 slug，它必须是目录本身返回过的——一个来自调用者并被写入某行 url 的 slug 会成为未来所有调用所运行的应用。

**授权配置在此处创建，而不是在某人的第一次点击时，并且它首先被创建。** SDK 自己的一步快捷方式会在任何人第一次按下 Connect 时按需创建一个，使用 Composio 的托管默认值和一个它自选的名称。在启用时创建它，以本部署命名，使它成为运维人员从应用存在的那一刻起就能在其 Composio 仪表板中看到的对象——并在那里收紧，无需更改代码。它先于此处写入任何内容，因此失败不会留下任何行，再次按下按钮就是完整的恢复。创建哪种配置取决于应用如何连接，而无需身份验证的应用则完全不创建，因为 Composio 拒绝为它持有配置——这是下一节的内容。

然后**针对该配置**附加一个账户，无论是通过为授权页面生成的链接，还是通过某人输入的密钥，这就是为什么之后不会再生成配置：在仪表板中删除了配置的应用会在 Connect 时拒绝，并指明管理员的步骤，而不是悄悄获取第二个无人命名或找不到的配置。

然后是一行普通的 `mcp_servers` 记录——id 为 `composio-<slug>`，url 为 `composio://<slug>`，来源为 `composio`，厂商为 Composio，标题来自目录，且没有任何形式的凭证——然后是应用的操作，记录每个操作的效果、破坏性标记和版本，因此错误的密钥会报告给刚刚按下按钮的管理员，而不是在 Bot 第一次调用某物时才发现。审计行是现有的 `configuration.changed` / `mcp_server_added`，标记为 `provenance: "composio"`。

没有任何东西是开启状态到达的。启用应用不指定任何 Bot，而为无人做出的授权画一个处于开启位置的开关，是这个代码库最一贯谨慎对待的事情。

### 3. 将操作授予 Bot

启用应用不会给任何 Bot 访问权限。从 `/admin/plugins/composio-<slug>` 的应用页面，打开一个 Bot 会得到一个列出每个操作及其开关的界面——可搜索，分为读取和写入，以*开启所有只读操作*作为唯一的批量操作，它在执行之前会说明该 Bot 将因此携带多少工具。之后每次调用都会检查授权、评估操作策略并写入审计行。

破坏性操作渲染为危险。没有任何东西渲染为安心：一个不声称具有破坏性的操作并不声称是安全的，因此标记的缺失以朴素方式绘制，绝不显示为绿色。

## 应用连接的四种方式

Composio 的目录不是一种流程套着一个名字。有些应用终止于人们见过上百次的授权页面；大多数终止于一个要求输入他们必须去找到的 API 密钥的框；少数则完全不向任何人要求任何东西。以 2026-09-13 的实时目录衡量，1540 个应用：

| 应用数 | 如何连接                                 | 要求什么，向谁要求                                      |
| ---: | ----------------------------------------------- | -------------------------------------------------------------- |
|  121 | Composio 自己的授权页面                   | 不向此处任何人要求任何东西。Composio 持有凭证        |
|   86 | 自行注册的 OAuth                     | 完全不向任何人要求任何东西。客户端在授权期间生成    |
| 1243 | 用户已持有的密钥               | 一到三个框，由连接的人输入             |
|   34 | 完全无需身份验证                        | 从不要求任何东西。没有账户可创建                     |
|   56 | 由运维人员注册的 OAuth 应用 | 此处完全不提供——见下方最后一节           |

**以前只有表格的第一行能工作。** 每个授权配置都创建为 `use_composio_managed_auth`，这对于 Composio 自己持有开发者凭证的应用是正确的对象，对其他所有应用则是错误的。对于自行注册的应用，失败是响亮的——Composio 没有自己的客户端可管理，因此它响应 404，应用根本无法添加。无需身份验证的应用以厂商自己的话失败，因为 Composio 根本不会为它持有配置。而对于密钥应用，它是安静且更糟的：配置被接受，然后每个被启用的人都被送到一个没有任何东西可问他们的授权页面。

**应用属于哪种类型，只推导一次然后记录下来。** 推导读取目录已发布的内容——`no_auth`、`composio_managed_auth_schemes`、`auth_schemes`——选择器和连接界面都读取那一个答案，而不是各自猜测。顺序是 `no_auth` 优先，这不是偏好：Composio 断然拒绝为无需身份验证的应用持有授权配置，因此应用在其旁边发布的任何其他内容都无法被采用。然后是托管 OAuth，因为它不向用户要求任何东西；然后是自行注册的 OAuth，它不向任何人要求任何东西；然后是需要用户已持有密钥的方案。Linear 同时发布托管 OAuth *和* API 密钥，正是因为这个原因解析为授权流程。

解析出的答案在管理员启用时写入应用的行（`mcp_servers.auth_scheme`），之后每一步——表单、连接调用、断开语句、调用门控——都读取该行而非目录。连接是对其创建时所针对的授权配置的持久附加，因此下个月开始为某应用发布新方案的厂商绝不能将活动连接转移到不同的流程上。因此再次按下 **Add** 不会重写方案，只有一个例外：在无人连接的地方没有什么可搁浅的，因此重写会发生，这是运维人员在不移除应用的情况下采纳厂商变更的方式。

### Composio 的授权页面，以及自行注册的 OAuth 应用

从这里看这两者是一种流程，这就是为什么前面的章节描述它们时没有区分：生成一个链接，用户离开前往 Composio 的页面，然后返回到本部署选择的页面。没有人输入任何东西，也没有人注册任何东西。

它们只在启用时创建的对象上不同。托管应用获得 `use_composio_managed_auth`，并搭乘 Composio 向厂商注册的开发者应用。自行注册的应用获得 `use_custom_auth` 和 `DCR_OAUTH`，**且完全没有凭证**，因为没有可持有的：客户端在某人授权的时刻向厂商注册。那一行中的 86 个应用不需要任何人的凭证——不需要 Composio 的，也不需要本部署运维人员的——它们在这里无法访问纯粹是因为被要求了错误类型的配置。

### 用户已持有的密钥

这是目录的大部分，也是没有授权页面的类型。密钥应用上的 **Connect** 不会离开 OpenBot：它询问 Composio 该应用需要什么，绘制那些框，之后的按下会携带框中输入的内容。

这些框是应用自己的。它们的名称、标签、帮助文本、默认值以及哪些是秘密的，由 Composio 按应用发布并逐字使用——大多数应用一个密钥，Shopify 一个密钥和一个工作区子域，Firecrawl 两个值——名称按原样发送回去，因为途中被重命名的名称就是某人填写了但没有任何应用会读取的框。Composio 标记为非用户可见的字段不会被绘制。任何非文本类型的字段，或完全没有名称的字段，是拒绝而非盲目绘制的框：某人将路径输入标有 *Certificate* 的框并被告知已连接，就是这个守卫存在所要阻止的失败。提交的名称如果应用未发布，也会被拒绝，而不是被丢弃——一个过时的表单以仍然匹配的那一半连接，是这里每个屏幕都绘制为正常工作的账户。

**输入的内容由 Composio 持有，绝不由此部署持有。** 这些值在一个请求中到达，在下一个调用中传送到 Composio，并在处理程序返回时消失。它们不写入表——`composio_connections` 仍然是一行只命名应用和人的记录，别无其他——不写入日志行，不写入错误体，也不写入审计行，审计行记录被填写的字段*名称*，绝不记录值。这个连接器为它们反转的唯一规则是它自己的：在其他所有地方，厂商抛出的对象作为 `cause` 被携带，因为它持有发起请求的内容，而在这一个调用上，那个请求是某人的密钥，因此适配器读取厂商的语句并完全丢弃该对象。代价是人们最常输错的流程上的诊断线索，而这个代价是明知故犯的：运维人员得到的是 Composio 自己的语句及其中的请求 id，这正是 Composio 仪表板所搜索的。

### 密钥只检查一次，页面会说明何时检查

**Composio 不会对提交的密钥进行评分。** 用明显错误的值创建的连接会返回 `ACTIVE`，并永远保持 `ACTIVE`。如果就这样放着，“已连接”将意味着“输入了某些东西”，而第一次失败会在数小时后出现在 Bot 对某人的回答中。

因此密钥连接之后恰好跟随一个调用：应用自己发布的一个只读、无参数的操作，由本部署从启用应用时记录的元数据中选择，绝不来自请求所说的任何内容。两个条件都是承重的，且互不蕴含。只读，因为探测绝不能改变任何东西——这里的“只读”意味着 Composio 将该操作标记为 `readOnlyHint`，因为所有未标记的都记录为写入。无参数，因为那一刻除了密钥之外对账户一无所知，因此任何必需的参数都必须被编造，而编造的参数会将*这个密钥好吗*变成*这个标识符存在吗*。两者结合不是双保险：Stripe 自己列表上第一个无参数操作是 `STRIPE_CREATE_BILLING_METER_EVENT_SESSION`，因此仅凭“不接受参数”选择的探测会为了查明某人的密钥是否有效而写入其账户。在应用发布身份形状的名称时优先选择它，而大多数应用发布的是其他安全的读取操作。

这是本部署中唯一一个没有 Bot、没有授权检查、没有策略评估、没有内容检查或 `mcp.call_*` 行就到达厂商的调用，因为没有 Bot
