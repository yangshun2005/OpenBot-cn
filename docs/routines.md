# 例程

例程是一种常驻指令：Bot 按计划执行某项任务，而不是等待被要求时才执行。“每个工作日九点，总结这个频道一夜之间发生了什么变化”就是一个例程，而不是一条消息——它会自行触发，只要保持开启就会一直运行，其回复会像该 Bot 发出的任何其他消息一样落入频道中。

## 创建例程

没有用于创建例程的表单。在频道中向 Bot 提出请求：“每个工作日九点，在这里发布站会笔记。”将一句话转换为五字段的 cron 表达式和一个频道，属于对话式工作，而这正是对话的用途所在。同一个 Bot 可以通过被要求来列出当前常驻的例程、修改某个例程或删除某个例程。

**前提条件：** Bot 只有在管理员授予权限后才能执行此操作。例程和其他功能一样是一个目录条目——`create_routine`、`update_routine` 和 `delete_routine` 是其写入工具——启用该条目并不会让任何 Bot 自动获得访问权限。每个工具都在 `/admin/plugins/routines` 按 Bot 逐一授予，就像 Google Drive 或 Notion 工具一样。管理员先决定哪些 Bot 可以调度未来的工作，然后才决定这些工作是什么；一个没有这三个工具中任何一个的 Bot 仍然可以被要求执行，但它会表示自己无法做到。

例程归属于请求创建它的人，并以该人的身份运行。参见[例程以谁的身份运行](#例程以谁的身份运行)。

## 15 分钟下限与 20 个启用上限

例程最多每 15 分钟触发一次。设置下限是因为模型可以被一句话说服去做任何一句话能描述的事情，包括“每分钟一次”，而下限是一句话无法说服逾越的界限。

一个人最多可以同时开启 20 个例程。设置上限的原因与下限相同：对话是一个容易在不经意间积累常驻工作的地方，而 20 是一个人自己的列表不再能记住的上限。关闭一个例程会释放一个名额；不需要删除。

## 疲劳规则

失败的例程只会发布一条关于失败的消息——即成功之后的第一次失败，而不是每次失败都发布。连续十次失败会关闭该例程，并发布第二条也是最后一条消息说明此事；在有人重新开启之前，不会再触发任何内容。重新开启会重新开始计数：只有自例程上次开启以来的失败才计入这十次。

这刻意不是一种重试策略。重试策略回答的是“这一次尝试是否通过了一个暂时失败的调度”——比如队列繁忙、服务器打了个嗝——而这个问题已经由共享工作队列自身的尝试计数在例程轮到运行之前悄然回答了。疲劳规则回答的是另一个问题：这个例程是否值得触发。一个在三月份过期的 Notion token 会每晚干净利落地失败一次，无论对任何一晚的尝试重试多少次都无法解决——只有关闭它并说明原因才能解决。

## 错过的窗口会被跳过，而不是重放

例程的下一次运行是一个时间戳，而不是一个队列。如果没有任何东西在监视时钟——比如一个从未启动的 worker，或者一个停机了一个月的 worker——例程的时间戳就会落后，而部署并不欠它错过的每一次触发：追赶是一种静默的消耗，而不是一次爆发。一个 worker 在沉寂一个月后恢复的部署，会通过逐次推进时间戳而不触发任何内容来消耗积压，直到时间戳重新变为当前时间——而不是触发三十个不同早晨的三十份过期摘要。

如果某次触发仍然足够新、值得执行，它仍然会发生。一个重启的服务器 pod 最多丢失停机时正在进行的那一次触发；下一次会按计划触发，因为在那次触发被尝试之前时钟已经向前走了。一个持续停机的服务器会丢失更多：每一个时间戳在没有任何东西能执行它时超过宽限窗口的触发都会被跳过，而不仅仅是正在进行的那一次。

## Worker 要求

没有第二个进程，上述任何功能都不会发生。API 服务器在被交付一次运行时，会响应 `/internal/routines/run`，但没有任何东西会自行交付给它——那是一个独立 worker 的全部职责，而一个从未启动过 worker 的部署不会调度任何内容。

这过去会静默失败。在聊天中创建的例程会被存储，其计划会被计算，而例程页面会像其他例程一样显示它有一个下次运行时间——因为就那个页面所知，它是正确的。一个没有 worker 的部署看起来与正常运行的一模一样，直到没有任何人的站会笔记到达。

现在每次扫描都会在 `routine_sweeps` 中记录它发生过，而例程页面会读取它。一个有常驻例程但没有任何扫描的人会被告知：从未有 worker 签到过，或者上一次签到是什么时候。窗口是 `MINIMUM_INTERVAL_MS`——十五分钟，即例程自身计划已经具有的下限，因此比这更长的间隔是任何例程都不会想要的。一个调度频率低于此的 CronJob 在两次运行之间会显示为静默。

有两个设置承载此功能：

- **`WORKER_SHARED_SECRET`** —— worker 向 `/internal/routines/run` 出示的凭据。如果两侧都未配置，API 服务器会拒绝每一次交接，而 worker 在完全未配置时拒绝启动，而不是触发那些无人能证明来自它的例程。
- **`SERVER_INTERNAL_URL`** —— worker 到达此部署自身 API 服务器的地址。这是关于 worker 进程运行位置的事实，而不是关于部署的事实，因此它直接从环境读取，而不是从部署的其余配置中读取。

在 Kubernetes 上，`routines.enabled` 会开启一个 CronJob，按 `routines.schedule` 运行 `fire-routines.ts`，就像计算机清理器是一个 CronJob 而不是 API 内部的定时器一样——定时器会在每个副本中触发，而 CronJob 的单次运行会执行整个扫描一次。在笔记本电脑上，`scripts/start.sh` 会启动一个 worker 进程，该进程在循环中运行同一个扫描，而不是运行一次就退出，因此这两种形态是同一份代码在两个不同的时钟上做同一件事，而不是需要保持同步的两套实现。

## 例程以谁的身份运行

例程以创建它的人的身份运行，而不是以 Bot 的身份，也不是以管理员的身份。它的轮次是使用该人自己的授权构建的，因此它可以在深夜做他们自己在聊天中输入相同指令所能做的完全相同的事情，而不会更多——例程无法访问其创建者从未连接过的连接器，也无法发布到他们不在的频道中。它的回复会作为来自该 Bot 的普通消息发布到频道中：它会像任何其他 Bot 消息一样点亮收件人的未读圆点，并且它会出现在对话记录中，而不是任何单独的地方，因为就频道而言，这正是它的本质。

## 范围

本次发布的是核心功能：从聊天中创建、列出、修改和删除例程；计划、上限和疲劳规则；触发它们的 worker。在 [#193](https://github.com/CopilotKit/OpenBot/issues/193) 中列出了四项后续工作，该 Issue 现已关闭；其中第一项已经构建完成。审计行现在会说明它们所来自的运行是由什么启动的，因此通过读取该行而不是将时间戳与 `routine_runs` 关联，就能将例程的操作与同一个人自己的操作区分开来。参见[架构](architecture.md#what-started-a-run)。仍然未完成的有：没有针对他人例程的管理员视图，只有每个人为自己看到的按所有者限定的页面；除了扫描自身的认领限制之外，没有针对每个部署或每个 Bot 可同时运行多少例程的上限；租户包还不能像发布 agent、频道或技能那样发布例程。
